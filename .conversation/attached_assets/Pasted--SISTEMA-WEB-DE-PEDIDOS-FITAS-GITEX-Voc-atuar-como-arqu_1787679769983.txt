# SISTEMA WEB DE PEDIDOS — FITAS GITEX

Você atuará como **arquiteto de software sênior, desenvolvedor full-stack e especialista em sistemas comerciais/ERP**.

Quero desenvolver uma aplicação web empresarial para digitação de pedidos/orçamentos por representantes comerciais.

O projeto será desenvolvido no **Replit** utilizando o Replit Agent.

IMPORTANTE:

Não tente construir todo o sistema de uma única vez.

Primeiro analise os requisitos, crie a arquitetura, banco de dados e estrutura básica. Depois desenvolva cada módulo de maneira incremental.

Sempre priorize:

* simplicidade;
* segurança;
* manutenibilidade;

* responsividade;
* código organizado;
* regras de negócio centralizadas;
* facilidade de integração com ERP.

# 7. PRODUTOS

Além desses campos, existem QUATRO CAMPOS OBRIGATÓRIOS provenientes do ERP:

### GRUPO

Nome técnico sugerido:

`group_code`

Formato:

ASCII / texto com exatamente até 2 caracteres.

Exemplo:

`01`

Nunca converter automaticamente para número, pois zeros à esquerda devem ser preservados.

---

### TIPO

Nome técnico sugerido:

`type_code`

Formato:

ASCII / texto com exatamente até 2 caracteres.

Exemplo:

`02`

Nunca converter automaticamente para número.

---

### PRODUTO

Nome técnico sugerido:

`product_code`

Formato:

ASCII / texto com exatamente até 4 caracteres.

Exemplo:

`0025`

Nunca remover zeros à esquerda.

---

### REFERÊNCIA

Nome técnico sugerido:

`reference_code`

Formato:

ASCII / texto com exatamente até 8 caracteres.

Exemplo:

`00001234`

Nunca converter automaticamente para número.

---

Esses quatro campos são importantes para integração com o ERP.

Eles serão utilizados para:

* identificar produtos;
* pesquisar produtos;
* incluir produtos no orçamento/pedido;
* enviar posteriormente o item para o ERP.

Considerar a combinação:

`GRUPO + TIPO + PRODUTO + REFERÊNCIA`

como uma identificação comercial/ERP importante do produto.

Criar índice adequado no PostgreSQL para melhorar pesquisas utilizando esses campos.

Avaliar também criar uma constraint UNIQUE composta, caso seja tecnicamente adequado:

`group_code + type_code + product_code + reference_code`

Não criar a constraint sem antes verificar se essa combinação realmente pode ser considerada única.

# 10. TABELAS DE PREÇO

Existirão três níveis de preços:

3. PREÇO PADRÃO

---

# 11. REGRA DE PREÇO

Criar um serviço central chamado:

`PricingService`

Quando determinado produto for incluído em um orçamento:

### PASSO 1

Pesquisar se existe preço específico para:

CLIENTE + PRODUTO.

Se existir:

usar preço do cliente.

Origem:

`CUSTOMER`

### PASSO 2

Caso não exista preço do cliente, pesquisar:

REPRESENTANTE + PRODUTO.

Se existir:

usar preço do representante.

Origem:

`REPRESENTATIVE`

### PASSO 3

Caso também não exista:

utilizar preço padrão.

Origem:

`STANDARD`

Portanto:

CLIENTE
↓
REPRESENTANTE
↓
PADRÃO

Essa ordem é obrigatória.

---

# 12. PREÇO ESPECIAL

O representante poderá informar um preço especial para determinado item quando permitido pelas regras do sistema.

Quando houver preço especial:

* armazenar o preço originalmente sugerido;
* armazenar a origem do preço sugerido;
* armazenar o preço especial;
* marcar `is_special_price = true`;
* utilizar `SPECIAL` como origem efetiva do preço.

Itens com preço especial NÃO recebem os descontos da capa do pedido.

O sistema deverá manter histórico suficiente para auditoria.

---

# 13. DESCONTOS

A capa do orçamento terá quatro descontos:

* Desconto 1
* Desconto 2
* Desconto 3
* Desconto 4

Todos serão percentuais.

Os descontos devem ser aplicados EM CASCATA.

Exemplo:

Preço:

R$ 100,00

Descontos:

10%
5%
3%
2%

Cálculo correto:

100 × 0,90 × 0,95 × 0,97 × 0,98

NÃO calcular:

100 - 20%

Criar:

`DiscountService`

para centralizar essa regra.

---

# 14. DESCONTOS NOS ITENS

Os descontos informados na capa deverão ser replicados em cada item.

Cada item deverá armazenar:

* discount1
* discount2
* discount3
* discount4

Isso é importante porque precisamos preservar as condições comerciais existentes quando o pedido foi criado.

Não depender das configurações atuais para reconstruir um pedido antigo.

Se o item possuir preço especial:

NÃO aplicar os quatro descontos ao cálculo daquele item.

Mesmo assim, preservar de maneira auditável quais descontos estavam informados na capa do pedido.

Criar uma flag como:

`discounts_applied`

para indicar se os descontos foram efetivamente aplicados naquele item.
