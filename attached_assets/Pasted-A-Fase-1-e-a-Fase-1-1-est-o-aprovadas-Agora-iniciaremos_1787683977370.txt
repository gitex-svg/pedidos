# FASE 2 — CADASTROS E SINCRONIZAÇÃO INICIAL COM ERP

Nesta fase implemente os cadastros-base que serão utilizados posteriormente pelo sistema de pedidos.

IMPORTANTE:

O ERP será a FONTE PRINCIPAL dos cadastros.

Portanto, não criar telas CRUD completas para manutenção manual desses cadastros.

O sistema web deverá:

ERP → API → PostgreSQL → Sistema Web

Os cadastros deverão ser sincronizados através de API e posteriormente consultados pela aplicação.

Nesta fase ainda NÃO implementar:

* pedidos;
* itens de pedido;
* descontos;
* preço especial;
* digitação de orçamento;
* sincronização de pedidos para o ERP.

# 2. REPRESENTANTES

O ERP será responsável por sincronizar representantes.

Manter pelo menos:

* id UUID interno
* erp_code
* name
* email
* user_id
* active
* source_updated_at
* last_synced_at
* created_at
* updated_at

`erp_code` deverá identificar o representante no ERP.

Não utilizar `erp_code` como primary key.

Criar índice/constraint apropriado para impedir representantes duplicados pelo mesmo código ERP.

A sincronização deverá utilizar UPSERT.

IMPORTANTE:

O vínculo entre:

representative.user_id

e:

users.id

é uma informação interna do sistema e NÃO deverá ser sobrescrita indiscriminadamente pela sincronização do ERP.

# 14. AUTENTICAÇÃO ERP

Implementar inicialmente uma solução server-to-server simples e segura.

Preferência inicial:

API Key forte enviada através de header.

Por exemplo conceitual:

Authorization: Bearer <ERP_API_KEY>

ou header equivalente.

A chave deverá existir SOMENTE em variável de ambiente/Secret do Replit.

Nunca:

* salvar no banco em texto aberto;
* incluir no frontend;
* incluir em logs;
* retornar em erros;
* colocar no Git.

Utilizar comparação segura quando aplicável.

Preparar arquitetura para futuramente migrar para HMAC caso seja necessário.

---

# 15. IDEMPOTÊNCIA / UPSERT

Todos os endpoints de sincronização deverão ser idempotentes.

Exemplo:

ERP envia produto 123.

Sistema cria.

ERP envia novamente produto 123.

Sistema ATUALIZA.

Não cria outro produto.

Utilizar:

erp_id

ou:

erp_code

conforme a entidade.

Definir claramente qual identificador externo será utilizado para cada cadastro.

---

# 16. SINCRONIZAÇÃO EM LOTE

Os endpoints deverão aceitar múltiplos registros por requisição.

Exemplo conceitual:

{
"items": [
{...},
{...},
{...}
]
}

Não obrigar o ERP a fazer uma requisição HTTP individual para cada produto.

Definir um limite razoável por lote.

Sugestão inicial:

500 registros.

Se considerar outro limite mais apropriado, explique.

A resposta deverá informar pelo menos:

* recebidos;
* criados;
* atualizados;
* ignorados;
* erros.

Erros individuais deverão identificar o registro sem expor dados sensíveis.

Avalie cuidadosamente se um registro inválido deverá invalidar todo o lote ou apenas aquele item.

Prefira estratégia que facilite reprocessamento pelo ERP.

---

# 17. DATA/HORA DO ERP

Quando o ERP enviar a data de última alteração do registro, armazenar em:

source_updated_at

Depois de sincronizar:

last_synced_at = horário atual do sistema.

Se receber posteriormente um registro com `source_updated_at` anterior ao já armazenado, não sobrescrever silenciosamente uma versão mais nova.

Definir comportamento e documentar.

---

# 18. INATIVAÇÃO

Cadastros sincronizados não deverão ser fisicamente excluídos.

ERP deverá poder enviar:

O sistema deverá manter o registro e marcá-lo como inativo.

Isso é importante para histórico futuro de pedidos.
