# FASE 5 — INTEGRAÇÃO DE PEDIDOS COM ERP E STATUS

A Fase 4 está concluída e aprovada.

Agora implemente a integração de saída dos pedidos finalizados para o ERP e o retorno dos status comerciais.

Nesta fase implementar:

* disponibilização de pedidos `SUBMITTED` para o ERP;
* consulta da capa e itens pelo ERP;
* confirmação de importação;
* número do pedido criado no ERP;
* atualização de status comercial;
* histórico de status;
* idempotência;
* proteção contra importação duplicada;
* logs de integração;
* exibição dos status na interface.

IMPORTANTE:

O ERP irá BUSCAR os pedidos no sistema web.

O sistema web NÃO deverá obrigatoriamente enviar ativamente o pedido para o ERP.

Fluxo principal:

Sistema Web
→ pedido SUBMITTED
→ ERP consulta
→ ERP importa
→ ERP confirma
→ ERP atualiza status posteriormente.

---

# 1. PRINCÍPIO DE INTEGRAÇÃO

O sistema web é responsável por:

* receber a digitação;
* calcular os valores;
* congelar os dados comerciais;
* finalizar o pedido;
* disponibilizar o pedido para integração.

O ERP é responsável por:

* buscar pedidos disponíveis;
* importar o pedido;
* gerar seu próprio número;
* confirmar a importação;
* informar alterações posteriores de status.

Não duplicar regras comerciais da Fase 4 no ERP API.

A API deve entregar o snapshot definitivo gravado no pedido.

# 7. PEDIDOS DISPONÍVEIS PARA ERP

* `internal_status = SUBMITTED`;
* ainda não confirmados como importados pelo ERP.

Sugestão:

* `page = 1`
* `pageSize = 50`
* máximo = 100

Se considerar cursor mais apropriado para integração, pode utilizar cursor, mas explique a decisão.

---

# 8. CONCORRÊNCIA NA LEITURA

O fato de o ERP consultar um pedido NÃO significa que ele já foi importado.

Portanto:

GET `/erp/orders/submitted`

não deve marcar automaticamente como sincronizado.

O pedido somente passa a ser considerado importado quando houver confirmação explícita do ERP.

Isso é importante porque uma chamada HTTP pode ser concluída no sistema web e falhar antes da importação no ERP.

# 15. PRECISÃO NA API ERP

Preservar exatamente a estratégia da Fase 4.

## Valores unitários

Enviar como strings decimais com até 6 casas.

Exemplo:

`"2.994300"`

## Quantidades

Enviar como string decimal preservando a precisão necessária.

## Totais

Sempre 2 casas decimais.

Exemplo:

`"8.98"`

Não converter valores financeiros para JSON number se isso puder causar perda de precisão.

Preferir strings decimais.

---

# 16. TOTAL DO PEDIDO

O ERP receberá exatamente:

`orders.gross_total`

e:

`orders.net_total`

Esses valores já são:

`soma dos totais dos itens arredondados`

Não recalcular o pedido na API ERP usando preços unitários.

---

# 17. CONFIRMAÇÃO DE IMPORTAÇÃO

Criar endpoint:

POST `/api/v1/erp/orders/:id/confirm`

O ERP chamará após importar o pedido com sucesso.

Payload conceitual:

```json
{
  "erp_order_number": "123456",
  "erp_import_id": "opcional-identificador-unico",
  "status": "EM_ANALISE",
  "source_updated_at": "2026-08-26T12:30:00Z"
}
```

Ao confirmar:

* validar pedido SUBMITTED;
* salvar número ERP;
* salvar `erp_synced_at`;
* salvar identificador externo, quando utilizado;
* atualizar `erp_status` quando fornecido;
* criar histórico;
* registrar integration log.

Executar em transação.

---

# 18. IDEMPOTÊNCIA DA CONFIRMAÇÃO

A confirmação precisa ser idempotente.

Exemplo:

ERP importa pedido 100.

Chama confirm.

A resposta chega ou não chega ao ERP.

ERP repete a mesma chamada.

A segunda chamada NÃO pode:

* duplicar histórico indevidamente;
* alterar número de forma incorreta;
* gerar inconsistência;
* falhar simplesmente porque a primeira já foi processada.

Se os dados forem idênticos:

retornar sucesso idempotente.

---

# 19. CONFLITO NA CONFIRMAÇÃO

Se pedido já estiver vinculado a:

`erp_order_number = 123456`

e chegar posteriormente confirmação informando:

`erp_order_number = 999999`

não sobrescrever silenciosamente.

Retornar erro de conflito.

Sugestão:

HTTP `409`

Motivo:

`ERP_ORDER_NUMBER_CONFLICT`

Registrar log sem expor informação sensível.
