# FASE 6 — HOMOLOGAÇÃO, SEGURANÇA E PREPARAÇÃO PARA PRODUÇÃO

As Fases 1 a 5 do sistema Pedidos Fitas Gitex estão concluídas e aprovadas.

O sistema já possui:

* autenticação;
* usuários ADMIN e REPRESENTATIVE;
* isolamento por representante;
* representantes;
* clientes;
* produtos;
* condições de pagamento;
* transportadoras;
* sincronização ERP;
* tabelas de preço;
* hierarquia CUSTOMER → REPRESENTATIVE → STANDARD;
* PricingService;
* orçamentos/pedidos;
* itens;
* snapshots comerciais;
* quatro descontos em cascata;
* preço especial;
* cálculos financeiros;
* finalização;
* fila de pedidos para ERP;
* confirmação de importação;
* atualização de status ERP;
* histórico;
* logs;
* OpenAPI;
* interface responsiva.

A Fase 6 NÃO é uma fase de novas funcionalidades comerciais.

O objetivo é:

**homologar, estabilizar, proteger, medir e preparar o sistema existente para produção.**

---

# 1. REGRA PRINCIPAL DA FASE

NÃO implementar novas funcionalidades comerciais.

NÃO alterar regras aprovadas das Fases 1–5 sem encontrar um problema real.

NÃO fazer grandes refatorações apenas por preferência arquitetural.

NÃO substituir bibliotecas estáveis sem necessidade.

NÃO alterar contratos ERP existentes sem motivo comprovado.

Prioridades:

1. estabilidade;
2. segurança;
3. integridade;
4. homologação;
5. observabilidade;
6. performance;
7. recuperação;
8. preparação para produção.

Se encontrar problema:

1. documentar;
2. classificar gravidade;
3. corrigir com a menor alteração segura possível;
4. criar teste de regressão;
5. validar novamente.

---

# 2. AMBIENTES

Formalizar três ambientes:

* DEVELOPMENT
* HOMOLOGATION
* PRODUCTION

Cada ambiente deverá possuir configurações independentes.

Separar especialmente:

* `DATABASE_URL`
* `SESSION_SECRET`
* `BETTER_AUTH_URL`
* `ERP_API_KEY`
* URL pública da aplicação
* origens permitidas
* nível de log
* configurações específicas do ambiente

Nunca reutilizar credenciais de produção em desenvolvimento.

Documentar a estratégia.

---

# 3. VALIDAÇÃO DE CONFIGURAÇÃO

Criar validação centralizada das variáveis obrigatórias.

A aplicação deve falhar rapidamente na inicialização quando uma configuração crítica estiver ausente ou inválida.

Por exemplo:

* DATABASE_URL
* SESSION_SECRET
* BETTER_AUTH_URL
* ERP_API_KEY

Não imprimir o conteúdo dos Secrets no erro.

Exemplo:

`ERP_API_KEY is required`

e nunca:

`ERP_API_KEY abc123...`

---

# 9. REQUEST ID

Toda requisição HTTP deve possuir um identificador:

`request_id`

Se não existir, gerar UUID.

Utilizar nos logs.

Quando apropriado retornar:

`X-Request-Id`

Isso é diferente de:

`correlation_id`

O `request_id` identifica uma requisição HTTP.

O `correlation_id` acompanha uma operação de integração ERP.

# 39. FALHA ENTRE IMPORTAÇÃO E CONFIRMAÇÃO

Simular:

ERP consulta pedido.

ERP importa.

POST confirm.

Depois ERP consulta novamente.

Esperado:

pedido ainda disponível.

Após confirmação:

pedido sai da fila.

# 40. CONFIRMAÇÃO REPETIDA
