## 1. Autenticação

Atualmente o Better Auth está sendo utilizado apenas para hash e verificação de senha, enquanto criação, armazenamento, expiração e invalidação das sessões foram implementados manualmente.

Quero reduzir código de segurança desenvolvido internamente.

Analise a implementação atual e proponha a melhor opção entre:

1. migrar completamente autenticação e gerenciamento de sessões para Better Auth;
2. manter a autenticação atual somente se houver uma justificativa técnica forte.

Dê preferência ao Better Auth completo se ele for compatível com a arquitetura atual React/Vite + Express + PostgreSQL + Drizzle.

Antes da alteração, explique resumidamente:

* o que será substituído;
* quais tabelas serão afetadas;
* impacto sobre `users`;
* impacto sobre `sessions`;
* impacto sobre cookies;
* impacto sobre `requireAuth`;
* impacto sobre `requireRole`;
* impacto sobre os testes existentes.

Depois implemente a solução escolhida.

Não quebre os contratos existentes desnecessariamente:

* POST `/api/v1/auth/login`
* GET `/api/v1/auth/me`
* POST `/api/v1/auth/logout`

Se precisar alterá-los, explique antes.

## 2. Teste de usuário inativo

Criar teste automatizado específico comprovando que:

`active = false`

impede autenticação.

O teste deverá validar que um usuário inativo:

* não consegue fazer login;
* não recebe sessão válida;
* não consegue acessar endpoints protegidos.

---

## 3. Rota ADMIN real

Criar uma rota administrativa simples para validar a autorização real.

Sugestão:

GET `/api/v1/admin/health`

Ela deverá exigir:

`requireAuth`

e:

`requireRole("ADMIN")`

Resultado esperado:

ADMIN → HTTP 200

REPRESENTATIVE → HTTP 403

Sem autenticação → HTTP 401

Não colocar nenhuma informação sensível nessa rota.

Criar testes HTTP reais para os três cenários.

---

## 4. Representante vinculado à sessão

Prepare a autenticação para que futuramente possamos determinar automaticamente qual representante está associado ao usuário.

Quando o usuário autenticado possuir role:

`REPRESENTATIVE`

o backend deverá conseguir resolver:

`user.id → representatives.user_id → representative.id`

Criar um helper/service centralizado para isso.

Sugestão conceitual:

`getAuthenticatedRepresentative()`

ou nomenclatura equivalente adequada à arquitetura atual.

IMPORTANTE:

No futuro, endpoints comerciais nunca deverão receber e confiar livremente em:

`representative_id`

enviado pelo frontend.

O representante deverá ser determinado pela sessão autenticada.

Ainda NÃO criar clientes ou pedidos nesta etapa.
