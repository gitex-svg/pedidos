# FASE 3 — MOTOR DE PREÇOS

A Fase 2 está concluída e aprovada.

Agora implemente exclusivamente o mecanismo de tabelas de preço e resolução de preço.

NÃO implementar ainda:

* criação de pedidos;
* itens de pedido;
* descontos;
* preço especial;

O objetivo desta fase é deixar o motor de preços completo, testado e pronto para ser utilizado futuramente pelos itens do pedido.

---

# 1. REGRA PRINCIPAL

A resolução de preço deve seguir obrigatoriamente esta ordem:

1. CLIENTE
2. REPRESENTANTE
3. PADRÃO

Ou seja:

CLIENTE → REPRESENTANTE → PADRÃO

Quando um produto for consultado para determinado cliente:

## Passo 1

Verificar se existe preço válido para:

cliente + produto

Se existir:

retornar preço do cliente.

Origem:

`CUSTOMER`

## Passo 2

Se não existir preço do cliente:

verificar preço para:

representante + produto

Se existir:

retornar preço do representante.

Origem:

`REPRESENTATIVE`

## Passo 3

Se não existir nos níveis anteriores:

verificar preço padrão do produto.

Se existir:

retornar preço padrão.

Origem:

`STANDARD`

Se não existir preço em nenhuma tabela:

retornar resultado explícito de preço não encontrado.

Não retornar zero silenciosamente.

`price_type`

Valores:

* STANDARD
* REPRESENTATIVE
* CUSTOMER

# 3. REGRAS DE ESCOPO

Aplicar constraints de integridade.

## STANDARD

Quando:

`price_type = STANDARD`

deve possuir:

* representative_id = NULL
* customer_id = NULL

## REPRESENTATIVE

Quando:

`price_type = REPRESENTATIVE`

deve possuir:

* representative_id preenchido
* customer_id = NULL

## CUSTOMER

Quando:

`price_type = CUSTOMER`

deve possuir:

* customer_id preenchido

O representante pode ser obtido através do cliente.

Evitar redundância desnecessária.

Criar constraints PostgreSQL quando tecnicamente adequado.

# 4. ITENS DA TABELA

`price_table_items`

---

# 5. PRECISÃO FINANCEIRA

Utilizar:

`unit_price NUMERIC(18,6)`

Não utilizar float/double.

Não realizar aritmética financeira crítica utilizando diretamente `number` de JavaScript.

Utilizar biblioteca decimal apropriada, se necessário.

Documentar a estratégia utilizada.

---

# 6. VIGÊNCIA

Uma tabela só pode ser utilizada se:

`active = true`

e:

`valid_from` for NULL ou menor/igual à data de referência

e:

`valid_until` for NULL ou maior/igual à data de referência.

Criar uma regra centralizada.

A consulta de preço deverá aceitar uma data de referência.

Se nenhuma data for informada internamente:

usar a data/hora atual do servidor.

Preparar o serviço para futuramente permitir preço histórico.

---

# 7. MÚLTIPLAS TABELAS

O sistema deve evitar ambiguidade.

Se houver mais de uma tabela ativa e válida no mesmo escopo:

exemplo:

duas tabelas CUSTOMER válidas para o mesmo cliente

não escolher arbitrariamente.

Definir política explícita.

Preferência:

impedir esse estado através de regras/constraints quando possível.

Se não for possível garantir completamente pelo banco devido às datas de vigência:

o `PricingService` deverá detectar ambiguidade e retornar erro técnico explícito.

Não escolher silenciosamente a primeira tabela.

---

# 8. PRICING SERVICE

Implementar de fato o:

`PricingService`

Criar um método conceitualmente equivalente a:

`resolvePrice()`

Entrada:

* customerId
* productId
* referenceDate opcional

O representante NÃO deve ser informado livremente pelo frontend.

O serviço deverá obter:

customer.representative_id

e utilizá-lo para o fallback de preço do representante.

Fluxo:

customer
↓
customer.representative_id
↓
CUSTOMER price
↓ se não houver
REPRESENTATIVE price
↓ se não houver
STANDARD price

---

# 9. RESULTADO

O serviço deve retornar estrutura clara.

Exemplo conceitual:

```json
{
  "found": true,
  "productId": "uuid",
  "customerId": "uuid",
  "representativeId": "uuid",
  "unitPrice": "3.250000",
  "origin": "CUSTOMER",
  "priceTableId": "uuid",
  "priceTableErpCode": "TAB001"
}
```

Quando não encontrar:

```json
{
  "found": false,
  "productId": "uuid",
  "customerId": "uuid"
}
```

Não utilizar:

`unitPrice = 0`

para indicar ausência de preço.
